# 文件修改冲突保护

用户已确认：修改文件时加锁，锁内核对上次读取的哈希；哈希按 Session 保存。
本项目用于学习，以代码简洁、易读为先。

## 方案

- 仅短时加锁不能防止旧内容覆盖；仅检查哈希不能保证检查与写入之间不被插入修改。
- 采用两者结合：非阻塞文件锁 + 锁内 SHA-256 校验，复用现有文件工具和 Session。
- 不增加模型工具、图节点或重试队列。

## 行为

- 所有文件工具按解析后的真实绝对路径协调访问。
- 锁放在项目根目录 `.mini-harness/file-locks/`，主智能体、子智能体和同项目会话共享。
  使用稳定的旁路锁文件，避免目标文件创建、删除后锁失效。
- 获取锁失败直接返回错误，包含文件和占用它的 Session ID；不等待。
- `read_file` 保持分页和原始换行，记录完整文件的哈希。
- 压缩后的自动重读不推进哈希，避免未送达模型的附件提前确认版本；忙文件跳过。
- 哈希保存在各自 `runtime.sqlite` 的 `metadata.file_versions`：绝对路径 → SHA-256。
- 修改已有文件前须先读取；新建文件可直接创建。成功修改后更新本 Session 的哈希。
- 内容变化则拒绝写入并提示重新读取，保留其他智能体的改动。
- 读取发现文件已删除时记录缺失状态，后续可以显式重新创建。
- 文件操作发生异常也关闭锁句柄；进程退出后由操作系统释放锁。

## 边界与验证

保护采用相同锁协议的内置文件工具。Bash、MCP 和外部编辑器不会自动遵守锁；
它们已经完成的改动仍能被哈希检查发现，但不保证它们与工具之间的并发写入安全。

验证两个 Session 的旧版本覆盖、编辑冲突、恢复后的哈希、分页的完整文件哈希、
路径别名、新建/未读文件、异常释放，以及真实子进程的锁竞争和模型错误反馈。
