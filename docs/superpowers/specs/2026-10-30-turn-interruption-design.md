# 对话打断

用户已确认：打断前台工具时先清理、保存配对结果，再接受下一轮；后台进程保留，已经发生的修改不回滚。

## 范围与实现选择

- 保留 Ctrl-C 作为打断入口，新消息沿用排队方式，不新增开关、图节点或通用调度层。
- 取消当前请求，等待前台 Bash 进程组清理；保存任务 ID、退出状态和日志路径。取消等待后台任务不停止后台进程。
- 文件工具的写入是没有 await 的短操作，完成后才会处理取消信号；不额外启用线程或屏蔽所有工具的取消。
- MCP 请求沿用 SDK 的取消机制。无法确认远端结果时标记未确认，不自动重试，不承诺撤销外部操作。
- 在 Harness 的取消出口整理并保存完整消息历史，补齐本批尚未执行的调用，清空待执行列表；已有结果优先复用。
- CLI 在清理完成后回到提示符。重复 Ctrl-C 不取消正在进行的清理。
- 用户打断后，后台完成通知继续入队，但不自动发起模型请求；显式聊天输入（包括已排队的聊天）恢复执行，/tasks、/stats 等命令不解除暂停。正常未打断时保留已有自动通知行为。
- 父轮次取消时，子智能体沿用已有中断和清理机制；恢复仍使用原子会话。空闲 Ctrl-C 暂停自动通知，不新增子智能体生命周期状态。

采用现有 asyncio 取消路径加一个 CLI 暂停标志，比另建中断节点或为每种工具配置调度策略更容易阅读；直接放弃当前等待会让前台进程和工具配对处于不确定状态，不采用。

## 验证

用真实图、SQLite、Bash 和本地 MCP 服务验证：前台清理、当前与未开始的调用配对、后台保留与通知暂停、重复 Ctrl-C、文件写入边界和半截模型回复。外部模型用离线替身；不操作用户真实会话或桌面。
